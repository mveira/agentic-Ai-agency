# Assumptions Approval

## Trigger
The prospect receives v1 requirements for review. This flow handles the confirmation, rejection, and iterative refinement of requirements and assumptions.

## Flow Steps
1. The prospect reviews each requirement and can confirm or reject it (with a `changeNote` explaining the rejection).
2. The prospect reviews each assumption and can approve or reject it (with a `comment` explaining the rejection).
3. **All confirmed**: Status transitions to `confirmed`. The KB is auto-populated (see below).
4. **Any rejection**: ChangeRequests are built from the rejected items. A new version is auto-regenerated by the RequirementsEngineerAgent. The review cycle repeats with the new version.
5. **Review handoff**: The agent suggests one of APPROVED, NEEDS_CLARIFICATION, or NOT_A_FIT. A human makes the final decision: APPROVED (build_ready) or REJECTED.
6. GHL milestone hooks fire on status transitions.

## KB Auto-Populate
On confirmation, `populateKBFromConfirmation()` is called:
- **Requirements** are stored as KB entries with type `requirement` and status `approved`.
- **Approved assumptions** are stored with type `assumption` and status `approved`.
- **Rejected assumptions** are stored with type `assumption` and status `rejected` (retained for audit trail).
- **Pending assumptions** are skipped and not stored.
- **Prior version entries** are superseded (they remain immutable as part of the audit trail).

## Agents Involved
- **RequirementsEngineerAgent** — Regenerates requirements when rejections produce ChangeRequests.

## Approval Points
- The prospect confirms or rejects each individual requirement and assumption.
- A human makes the final review decision (APPROVED or REJECTED), overriding the agent's suggestion if needed.

## Failure Handling
- **Regeneration LLM failure** — An error is returned. The new version is not created.
- **Version already confirmed** — A 409 Conflict is returned. Confirmed versions cannot be re-confirmed or modified.
